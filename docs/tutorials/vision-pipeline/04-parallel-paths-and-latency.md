# 04 — Parallel paths and latency

**Step in this chapter:** *(none — analyzes `pixel_result`'s already-generated design)* · **Tools needed:** Python

## Goal

See how FORGE proves two parallel paths of different real latency
reconverge on the exact same cycle, and what happens when that's wrong.

## What you will learn

- What an alignment delay is and why `threshold_rtl`'s branch needs one.
- How `forge analyze latency-check` verifies a merge point statically, before any simulation.
- What `edge_mask_merge_rtl`'s own runtime `tag_mismatch` check re-verifies at runtime.

## Starting design

`design_pixel_result.yml` (chapter 03), already gen-topped.

## What you add

Nothing new is built this chapter — this is a closer look at the merge
point chapter 03 already created:

```
window_builder_rtl (10 cycles) -> sobel_hls (4 cycles)              = 17 cycles
threshold_rtl (2 cycles), +12-cycle alignment delay                  = 17 cycles
                                              both -> edge_mask_merge_rtl
```

`delay_cycles: 12` on the threshold branch is a real design-level field
in `design_pixel_result.yml`, not a magic number — it exists so both
branches present the same logical pixel to `edge_mask_merge_rtl` on the
same cycle.

`out/reports/latency_check.md` — a Markdown report, regenerated by the

## Command to run

```bash
forge analyze latency-check plugins/vision_pipeline_demo/forge/designs/design_pixel_result.yml \
  --contracts-from plugins/vision_pipeline_demo/forge/modules.yml \
  --hls-build-root build_hls_vision_pipeline_demo
```

## Expected terminal result

```
✅ No latency mismatches detected (1 merge point(s) checked)
Report: out/reports/latency_check.md
```

## Artifacts to inspect

`out/reports/latency_check.md`'s real, generated content for this
design:

| Input path | Accumulated latency |
|---|---|
| `sobel → merge` | 17 |
| `thresh → merge` | 17 |

Both branches land on cycle 17 exactly (`norm`'s 3 cycles are common to
both, then `winbld(10)+sobel(4)=14` vs. `thresh(2)+delay_cycles(12)=14`
— 3+14=17 either way). `forge analyze latency-check` verifies this
statically, at `forge topgen validate` time, from each module's own
declared `latency:` — it never needs to run a simulation to catch a
misalignment.

`edge_mask_merge_rtl` itself re-verifies the same fact at runtime, via a
`tag_mismatch` output — see [chapter
12](12-diagnostics-and-negative-fixtures.md) for what happens when the
alignment delay is wrong and both checks catch it.

## Why the capability matters

Any design with two parallel paths of different depth needs this same
alignment proof — chapter 05's bounded/elastic join and chapter 09's
full-functional assembly both depend on the same
`forge.analyze.latency_static` machinery this chapter exercises
directly.

## Common failure

A misconfigured or missing alignment delay is exactly the kind of
mistake this static check exists to catch before simulation — see
[chapter 12](12-diagnostics-and-negative-fixtures.md).
